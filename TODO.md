Do not run discovery against any pattern other than `*.recruitee.com/*`, and do not promote a Personio or SmartRecruiters candidate (both remain parked per round 4).

**Transport health (apply after every batch in phases 4–5):** `(attempts − transportOrThrottleFailures) ÷ attempts`, where a transport/throttle failure is HTTP 429/5xx, timeout, or connection failure only. An `identity`-reason rejection (failed the domain-link check) and a `no_country_jobs`-reason rejection (verified but no India-eligible job) are both successful transport outcomes — the request completed and returned a valid, decisive answer — and must not count against this floor. Stop the round if any batch's transport health falls below 90%, or transport/throttle failures affect more than 10% of a batch.

**The round closes only when one of these applies:**

- the phase-3 yield check fails (fewer than 3 of the first 30 reach `matched`);
- a transport health floor above is breached in any batch;
- the Recruitee employer target is reached (TransPerfect plus nine net-new, counted only from this round's own successfully crawled sources whose partition independently contains at least one India-eligible job — never from a successful crawl alone, and never from verified-but-never-indexed admissions);
- phase 5 completes or exhausts the bounded crawl of everything phase 4 admitted — reaching the 40-attempt or 20-admission verification ceiling ends phase 4 but must not end the round before phase 5 runs against whatever was admitted.

**On low yield or exhausted caps without reaching the target:** close the round as a measured result (same pattern as round 3's Lever/Ashby phase-one closure) rather than expanding scope mid-round. A follow-up needs its own reviewed contract, not a silent cap increase.

## 14. Resume section/label recognition drops standard headings — draft for review

A live POC run (2026-08-25) against a real, unmodified full-stack resume PDF surfaced three related bugs in `src/candidate-profile.ts`'s deterministic fact extractor. The resume was ordinary, template-conforming, ATS-normal formatting — not malformed input — which makes this a parser-coverage gap, not a garbage-in case.

**Root causes, all in the same fixed-vocabulary mechanism:**

1. `sectionNames` (`src/candidate-profile.ts:162-168`) maps only `"experience"`, `"work experience"`, and `"employment"` to the experience section. The resume used `"Professional Experience"` — a mainstream heading, arguably as common as bare `"Experience"` in template-generated resumes (Novoresume, Zety, Canva, LinkedIn's own builder, most Word templates). Because the heading matched nothing, `section` stayed `undefined` for the entire block: **zero date, role, employer, or experience_statement facts were extracted from 4.5 years of work history**, including every quantified achievement bullet.
2. The same map has no `"projects"` variant covering `"Key Development Projects"` / `"Key Projects"` / `"Relevant Projects"`. Same failure mode: a project section demonstrating a claimed skill (React) produced zero facts.
3. `neutralLabels` (`:203`) and `skillSubheadings` (`:173`) — the sets used to strip a category label before splitting a skill line — cover `languages`, `programming languages`, `frameworks`, `databases`, `tools`, `cloud`, `platforms`, `technologies`, but not `frontend` or `backend`. A line like `Frontend: React.js, Angular, Next.js` therefore fails to strip the label, and `content.split(/[,;|]/)` yields a first value of the literal string `"Frontend: React.js"` instead of `"React.js"` — corrupting the fact so it can never match the `React` requirement definition. Same failure for `Backend: Node.js`.

**Measured effect:** the candidate's two most central, explicitly-stated skills (React, Node.js) never registered as evidence anywhere in `recommend_jobs` output, and several results showed `React` as an explicit **gap** on jobs that required it — a wrong claim, not just an incomplete one, since the resume does state the skill. With zero date facts, seniority/experience-duration alignment had no signal to use at all. Across the full India-eligible corpus (~6,978 jobs), the run returned zero `strong` fits.

**Fix requirements:**

- Widen `sectionNames` and the skill-label sets to cover the common real-world variants (at minimum: `professional experience`, `career history`, `relevant experience`, `work history` for experience; `key projects`, `key development projects`, `relevant projects`, `personal projects` for projects; `frontend`, `backend`, and a short review pass for other common category labels such as `devops`, `testing`) — audited the way the requirement vocabulary was audited (§12), not just patched to the three exact strings this one resume happened to use. Whack-a-moling the literal strings found here would leave the same class of bug for the next phrasing variant.
- This widening is lower-risk than the earlier `Go`/`Spring` requirement-matching bugs: heading/label recognition is a **whole-trimmed-line equality lookup against a map**, not a substring match inside free text, so it cannot reintroduce the false-positive-inside-prose failure mode those fixes had to guard against. Do not change that property — do not introduce fuzzy or substring heading matching as part of this fix.
- Add regression tests for: a resume using `"Professional Experience"` (asserts date/role/experience_statement facts extract), a resume using `"Key Development Projects"` (asserts project facts extract), and a resume with `Frontend:`/`Backend:` category-labeled skill lines (asserts clean per-skill values with no label residue). Use a synthetic fixture reproducing the same patterns — do not commit the real candidate's resume text or PII into the test suite.
- No regression on any currently-recognized heading or label; full existing suite must still pass.

Once implemented, re-run the same real resume through `recommend_jobs` to confirm React/Node.js resolve as clean skill facts, the experience-section facts appear, and check whether match quality improves as expected (more `strong` fits, React/Node.js credited instead of appearing as gaps) before considering this closed.

**Completed (2026-08-25):** the extractor now recognizes an audited set of common experience, project, skills-section, and colon-prefixed skill-category variants through exact normalized equality only; no fuzzy or prose-substring heading matching was introduced. Standalone skill subheadings retain a narrower low-ambiguity vocabulary so legitimate skills such as `Frontend`, `Backend`, `DevOps`, and `Testing` are not silently discarded. Synthetic tests cover the reported patterns plus the wider reviewed variants without including candidate text or PII. The private replay of the same untracked PDF produced clean React.js and Node.js skill facts, one date fact, role/employer and 23 experience/outcome facts, and seven project statements. With India + full-stack intent and React/Node.js requested, the top 100 changed from zero strong fits in the POC to 6 strong / 42 good / 52 stretch; React was credited on 21 results, Node.js on 1, and neither appeared as a gap. The replay used `refresh: never` and made no network request. The PDF remains untracked and was not copied into the test suite.

**Codex review (2026-08-27, first pass):** the first pass conflated a company-owned ATS board with a multi-employer aggregate feed under one `Source` concept — an aggregate feed structurally cannot pass company-board ownership verification, since there's no single company to verify. Availability precedence when signals conflict (`removed` > `expired` > `active` > `unknown`) is now explicit.

**Codex review (2026-08-27, second pass):** six further correctness gaps, not wording issues. A deterministic `runId` alone doesn't survive a crash — nothing preserved the crawl payload itself, so replay had nothing to replay; fixed with a durable local outbox (atomic file per pending run under `.openings/`, consumed only after SQLite commits). Migration claimed `complete: true` for backfilled runs on the theory that a live partition implies a complete crawl — but today's snapshot format carries no completeness signal at all, so that was an invented, unverifiable claim; migrated runs are now seeded `complete: unknown` and can still establish positive observations, just never `removed`. `Availability` precedence was applied without a freshness gate first, which would have let an old `removed` or `active` verdict stand as "current" forever; fixed to gate on the existing 14-day freshness window before precedence even applies, with reactivation stated explicitly as the natural consequence of always re-deriving from scratch. Aggregate-provider completeness needed a canonical `scope` (query/country/page-range) — an aggregate fetch is never "all of the provider," so absence is only meaningful between two runs of the identical scope. "After a successful crawl" (writing history) directly conflicted with "partial crawls record what they saw"; resolved with an explicit crawler result envelope that snapshot-replacement and history-ingestion both read independently, with different outcome filters. Tombstones can't claim to hold a "final Availability" once `Availability` is declared derived and freshness-sensitive — the tombstone now stores an explicitly labeled historical projection instead, and aggregate tombstones preserve the original `EmployerClaim` rather than implying a verified Employer link. Also added: `lastCheckedAt` keyed by origin (`sourceId` or `(providerId, scope)`), not always `sourceId`, since aggregate jobs have no `sourceId`; and a schema-version/foreign-key/`CHECK`-constraint requirement for the implementation itself.

**Codex review (2026-08-27, third pass):** the second pass's own `Availability` algorithm still didn't implement the reactivation it claimed in prose — precedence (`removed` > `expired` > `active`) was applied across *all* evidence inside the freshness window, so an older `removed` run could still outrank a genuinely newer `active` one by signal strength instead of losing to it on recency. Fixed: derivation now selects the single most recent same-scope run first, and precedence only resolves a *contemporaneous* conflict within that one run (e.g. present but past its own stated expiry) — a later run's evidence always supersedes an earlier one outright, which is what actually makes reactivation automatic. `CrawlRun.complete` was declared `boolean` while migration assigned it `unknown`; it's now explicitly tri-state (`true | false | unknown`), with only literal `true` ever authorizing a removal inference. The outbox was only sequenced ahead of the SQLite write; it's now sequenced ahead of *both* consumers (durability is the first thing that happens after a crawl completes, before snapshot publication or SQLite ingestion, so a crash immediately after crawl completion still can't lose the run). The implementation contract wrongly proposed a `CHECK` constraint on `Availability`, which is never stored — removed, with `CHECK`s scoped to the columns that actually exist (`CrawlRun.outcome`, `CrawlRun.complete`, `Provider.contentRights`), and a real `Scope` table now defined so `Job`/`JobObservation` → origin is an actual foreign key instead of a promised one, with `scopeHash` versioned and normalized so aggregate scope equality survives an adapter's query shape changing over time. Also added: aggregate-sourced jobs can be observed through more than one `Scope` (the same posting matching more than one query), so both `Availability` and `lastCheckedAt` are now derived per `(jobId, scopeId)` first and combined at the job level — presence in any one scope always wins over absence inferred in a different scope, since an absence inference is inherently bounded to the scope that produced it.

**Codex review (2026-08-27, fourth pass):** two remaining correctness gaps and one open decision, plus one still-unexecutable prerequisite. `Availability` selected the single most recent same-scope run and only then applied precedence — but a run that is merely *silent* about a job (failed, or partial and didn't happen to include it) isn't evidence, and letting it "win" by recency would drop a still-fresh verdict for no reason. Fixed: derivation now walks runs backward looking for the newest *authoritative* one — a run with a positive observation of the job, or a `complete: true` run proving absence by omission — skipping silent runs, which still advance `lastCheckedAt` but never move `Availability`. The outbox only tracked a SQLite acknowledgment, so an entry could be deleted before snapshot publication (the other consumer) had actually finished, losing the only durable copy if publication then failed; fixed with two independent, atomically-persisted acknowledgments (`sqliteAck`, `snapshotAck`, the latter explicitly `no-op` for outcomes that never touch the snapshot) and deletion gated on both. `JobObservation` was carrying its own `scopeId` in the implementation contract's FK list even though the entity's own definition already derives scope through `runId` — a second, independently-writable copy that could disagree with the run it belongs to; removed, scope is now only ever reached by joining through `CrawlRun`. The scope-version question is now decided rather than open: a `scopeVersion` bump creates a new `Scope` outright, and its predecessor is left to age to `unknown` through the existing freshness mechanism — no new alias/migration entity, since that would require judging two differently-shaped queries "the same scope" for continuity, the exact ambiguity `scopeHash` normalization exists to avoid. Last, the retention prototype's contract is now concrete instead of a placeholder: 14 consecutive calendar days, a named 5-source subset spanning every ATS adapter in the catalog (`abb`, `anthropic`, `bolna`, `mindtickle`, `transperfect`), explicit expected outputs, and explicit success/abort criteria — see decision-map #15 for the full numbers.

**Codex review (2026-08-27, fifth pass):** one race condition and three clarifications, plus a lifecycle-envelope gap. The dual outbox acknowledgment from the fourth pass was itself race-prone — two consumers reading the same unacknowledged entry and writing back independently could each overwrite the other's ack. Fixed by reusing this codebase's existing `withFileLock` (`src/file-lock.ts`, already used by `enrichment-registry.ts` and `company-seeds.ts` for the same class of problem) so read-ack-write-and-maybe-delete is one critical section per entry, not three unsynchronized steps. The crawler result envelope was a loose object shape with rules only stated in prose (`partial` shouldn't be `complete: true`, `failure` shouldn't carry observations); it's now a discriminated union on `outcome` so those combinations are structurally unrepresentable rather than relying on every call site remembering the rule. The `Job → Scope` relationship was wrong for aggregate jobs — prose elsewhere already said an aggregate job has no single origin, but the `Scope` entity and the FK list both still claimed a direct `Job → Scope` foreign key; fixed by giving only `single_employer` jobs a direct `sourceId` FK (with `Scope` trivially reachable from it) and deriving aggregate job–scope membership purely from `JobObservation` joined through `CrawlRun`, with no new membership table. The FK list is now complete (`Job.sourceId`, `Scope.sourceId`/`Scope.providerId` with an exactly-one-of `CHECK`, `Source.providerId`, `Source.employerId`, alongside the existing ones). "Durable" was undefined; it's now stated explicitly as process-crash safety only, matching what `atomicJson` already provides everywhere else in this codebase (no `fsync`, so not power-loss safety) — upgrading that is a separate, explicitly-scoped decision if ever needed. The prototype's daily cadence was unstated; each of the 5 sources now gets exactly one scheduled attempt per day, with up to 2 same-day retries counting toward that one attempt, never a second scheduled attempt. Tombstone/projection mechanics are now verified by one controlled synthetic transition rather than depending on a real source happening to remove a job in 14 days; real transition incidence is a measured output, and zero real transitions is recorded as `insufficient_evidence` (a valid result) rather than a failure or an unbounded restart.

**Codex review (2026-08-27, sixth pass):** two blockers on top of the fifth pass's fixes. `CrawlRun` and the retry model directly contradicted each other — "one row per crawl attempt" versus the prototype collapsing up to three tries into a single row. Resolved by splitting the two apart: `CrawlRun` is now one row per *scheduled* crawl (one per source per day), and a new child `CrawlAttempt` entity is one row per actual transport-level try within that run's retry cycle — the persisted source of truth the fourth pass's retry counts were missing, with `attemptCount` always derived from these rows rather than a separately-tracked integer. Adapter-internal HTTP retries stay invisible inside one `CrawlAttempt` (that's the adapter's own concern); a new `CrawlAttempt` exists only for a fresh invocation after a prior one outright failed. The outbox envelope is emitted once per `CrawlRun` after its retry cycle ends, now explicitly carrying the full `attempts` list so mid-cycle history can't be lost to a crash. Scope identity had no real uniqueness enforcement — an FK only constrains what points at a row, not how many rows can exist for one origin — so two indexes were added: a partial unique index on non-null `sourceId`, and a unique index on `(providerId, scopeVersion, scopeHash)` for aggregate scopes. The FK list was still missing `JobObservation.jobId`→`Job` and `CrawlAttempt.runId`→`CrawlRun`; both added. Provider-kind coherence (`Scope.sourceId` must resolve to a `single_employer` Provider; `Scope.providerId` must be `multi_employer_aggregate`) and "failure runs own no observations" can't be expressed as `CHECK` constraints in SQLite (`CHECK` can't reference another table), so both are now specified as `BEFORE INSERT`/`BEFORE UPDATE` triggers instead — one consistent mechanism for every cross-table invariant, with `CHECK` reserved for genuinely single-row rules. The `CrawlRun.outcome`/`complete` `CHECK` now directly encodes the envelope's discriminated union as one constraint (`complete = 'true'` requires `outcome = 'success'`; `partial`/`failure` require `complete = 'false'`; `success` + `unknown` stays explicitly allowed for migrated rows) instead of three prose rules that could drift apart from the type.

Not execution-ready as a build yet — this is the design decision, not an implementation plan. It still needs the deterministic export/report command that makes the SQLite store as reviewable as every JSON artifact in this project already is, and the 14-day prototype phase above must actually run before the retention window is set. Explicit non-goals, reaffirmed: no hosted API, accounts, or billing; no resume storage of any kind; no change to what `recommend_jobs`/`search_jobs` read until a later, separate decision proves parity.
